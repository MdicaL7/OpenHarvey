# 合同记忆 v2 实验结果分析

日期：2026-10-13。分析对象是已执行的测试记录，以及针对评分缺口完成的定向复测。本报告不重新运行测试集，不将执行完成等同于验收通过。

**结论：风险处置案例保存、带条件的跨合同参考、经验确认、人工版本保护及当前产品范围内的权限边界，已有真实记录支持。偏好曾出现“存得正确、查得误导、答得错误”的系统缺陷；修复后，新会话和同来源再提炼的定向复测支持该缺陷已被关闭。现有证据适合支持本机、少量团队、人工复核的辅助审查试用，不能支持无人值守审批、广泛合同类型的准确率承诺或整体生产验收通过。**

原始模型评分仍为 **6 通过、1 失败、2 待复核**，见[原始评分](judge-original-summary.json)。后续三项复核单独保存在[复核结果及逐字证据](analysis/review-results.json)，不改写旧结果。上下文压缩按用户要求另列为[OpenHarvey 接入／运行层问题](runtime-compaction-deferred.md)，不作为本轮记忆分析的阻塞项，也不列为全面验收通过。

## 1. 实际测试范围与证据口径

测试包准备了 10 份合同和 21 条业务事件，但本轮 v2 自动主链实际集中于 **H01、F01 两份设备采购合同**；另有 F01_R2 附件对照、浏览器路径 H02/F01，以及偏好、权限、故障与版本操作。不能将这次结果表述为“10 份合同、21 条事件全部验证通过”。审批记录、政策文件等材料的全量顺序输入没有本轮完整证据。

业务、提炼、相关性判断和 judge 均配置为 ChatGPT 订阅 `gpt-6.1-sol`；普通 provider 边界试验显式使用 DeepSeek。提炼与 judge 使用独立会话，但配置的是同一模型，不能视为独立模型交叉验证。CLI 没有返回可独立核验的实际解析模型 ID，记录仍为 `model_verified=false`。本报告不推断该限制之外的模型身份。

这里采用三档证据：

1. **存储正确**：实际业务回执、Core 条目、来源、版本和状态支持。
2. **检索正确**：真实接口或原生工具返回了正确版本，并保留条件与权限限制。
3. **Agent 实际采用正确**：在工具轨迹之后，最终回答使用了这些信息，且没有把历史意见当作当前合同事实或批准。

“回答中出现老师、60 天或历史经验”等关键词不够证明第三档；工具返回、当前正式状态和回答语义必须一致。

每组关键证据均为原始 JSON 中选取的实际值，附原文件 SHA256 和 JSON Pointer，见[证据索引](analysis/manifest.json)。完整原始记录保存在本机 `/Users/dicam/.local/share/openharvey/contract-v2-experiment/20261013/`；公开摘录不包含登录凭据。`core-03-audit` 是 `core-03` 的独立只读审计副本，补入按消息 ID 对齐的原生工具记录和历史案例版本，没有加入该步骤之后的未来对话。

## 2. L1–L3 在真实例子中的表现

### L1：记住了用户怎样处理风险，而非把条款摘录当作决定

H01 第5条原文是分期付款，未写60天。S005 中用户保存的是：若拟调整尾款为60天，可以在20%预付款前提下接受，仅限本项目，修订、批准和执行均未核验。实际案例 `case_f5d248be00e165f72a226245b13796d3@1` 保存了“接受风险”、用户备注、三个限制、供货方角色、报告及风险方案版本、合同文件哈希和原文段落，并把 `approval_status`、`execution_status` 留为 `not_verified`。[E01](analysis/records/E01.json)

这支持“风险卡片保存行为→可追溯处置案例”的结论。限制也很明确：用户备注只给出了条件，没有完整说明主观商业理由；不能据此宣称系统已准确还原用户未说出的动机。条款原文在这里是处置背景和证据，不是“已接受60天”的来源。

v2 的风险 L1 主要保存在 `review_cases`，长期偏好声明保存在另一类来源记录中。S005 的旧 `atoms` 数组为空，不等于没有 L1。实际跨合同检索走专用历史处置服务，返回案例 ID、版本、条件、差异及可访问来源。

F01 是相同买卖双方的二期项目，但第1条明确独立结算。S009 返回 H01 案例时标为 `conditional`，指出项目范围、拟议60天与现稿15个工作日、争议款和验收保障差异。S008 的最终回答也采用了这些限制。这里同时有存储、检索、采用三层证据。[E03](analysis/records/E03.json)

召回结果并非全部都是直接适用的命中。修改付款标准后，付款查询还返回一条解除风险案例，关系为 `insufficient`，理由是缺少当前解除结算及成本材料。这说明服务会保留关联较弱的候选及其不确定性；它没有冒充明确适用，但仍增加了人工筛选负担。不能把“返回三条”当成“三条检索准确”，也不能把信息不足条目直接转成处置建议。[E09](analysis/records/E09.json)

### L2：出现了带分支的方法，未把两个案例投票成一条统一标准

单个 H01 案例没有产生 L2。F01 保存“增加银行保函并核验后再讨论较长账期，不照搬20%预付款方案”后，候选正文区分了两个项目：H01 是附预付款条件的个案接受意见，F01 是增加保函后再评估的修改要求。它引用两个案例的明确版本，并写明“不能据此统一接受60天账期”。确认前正式列表为空，确认后才进入个人经验。[E02](analysis/records/E02.json)、[E04](analysis/records/E04.json)

后续原生 `scenario/read` 返回正式经验 `b7cdc700-a3ca-48cf-868d-1ec5af97c691` 的版本1。Agent 不仅复述经验，还读取 F01，指出原文没有60天或银行保函约定，20%首付款条款不等于到账，保函只是进一步讨论的前提。这比“回答提到历史经验”更强，是实际读取及条件应用的证据。[E05](analysis/records/E05.json)

这组经验仍保留 H01/F01 案例叙述，具有方法性但不是高度抽象、极短的规则。当前样本不足以证明在大量案例、复杂反例或不同合同类型下仍能稳定归纳，也没有统计性精确率／召回率。此次没有观察到付款专属方法被正式发布为企业统一 L3 原则；“跨多风险形成稳定审查原则”的能力仍缺少充分正例。

### L3：长期／临时识别成立过，最新版本采用曾失败，修复后有定向证据

明确的“以后”“今后”生成了报告结构与称呼两条个人正式偏好；“这次三句话、这次叫同事”没有长期候选。这证明这些明确表达的区分成立，而非证明所有自然语言时间范围均能识别。[E06](analysis/records/E06.json)

实质问题出现在人工更新之后：正式正文已经是“称呼用户为老师”版本2，原子查询仍返回“大哥”的旧用户声明，并以普通 `preference` 类型呈现。PREF-13 最终明确把“大哥”列为现行称呼，还说明不采用摘要中的“老师”。所以当时是：**存储正确，来源检索缺少有效性语义，Agent 采用错误。** 不能因答案里同时出现“老师”而判通过。[E10](analysis/records/E10.json)

修复没有删除旧原话或篡改历史。L1 查询现在明确标注 `historical_source`，同时返回带版本的 `current_formal_preferences`；Agent 指令要求最新正式正文优先于旧来源和未更新的标题。修复后新团队的新会话实际回答“当前称呼老师”，并将旧“大哥”列入“旧声明，仅用于溯源”；报告结构也采用人工修订的“原文证据与建议”。[E11](analysis/records/E11.json)

删除称呼后，新会话只列出仍有效的报告结构，没有把已删除称呼计入现行约定。随后正常对话触发真实 L3 再提炼，旧来源仍在输入中，模型甚至重新生成了旧内容，但这些内容没有绕过服务端的确认、人工保护和同来源抑制机制。[E12](analysis/records/E12.json)、[E13](analysis/records/E13.json)

## 3. 关键能力：存储、检索、采用必须分别看

|能力|存储层证据|检索层证据|Agent采用／业务结论|
|---|---|---|---|
|用户偏好|长期两条分存；临时要求不入长期候选|修复前旧声明误导；修复后同时标明历史来源和现行正式版本|修复后新会话正确采用老师及人工报告结构；不承诺每次自然答复都重复称呼|
|经验沉淀|单合同不凑 L2；两个合同形成候选，确认才生效|真实正文读取与正式条目版本一致|真实回答保留预付款／保函分支及项目限制；更大样本泛化尚未证明|
|跨合同召回|历史意见与报告、合同版本绑定|三风险均找到对应案例，允许有解释的关联风险；相反角色排除|付款有明确采用证据；不能把同风险编号或同一交易方视为充分适用条件|
|记忆更新|修改形成新版本，历史未覆盖|撤回案例退出结果；依赖旧版本的 L2 标为需复核|旧报告正文不被后续记忆自动改写；所有更新场景的自然语言采用未穷举|

候选、已确认记忆、合同审批是三个不同状态。当前实验支持“确认后进入经验／偏好”，没有证明“确认卡片即完成合同审批”；实际案例也没有把保存意见或报告当成已批准、已付款、已修改。

## 4. 失败及复核结论

### 原始评分原样保留，复核不重算一个整体通过率

|---|---|---|---|
|偏好|fail|原评分把助手回复中的确认说明当成正式正文污染，并要求某次普通回答必须出现昵称：评分口径错误。随后实际发现旧L1覆盖人工L3：真实系统缺陷。旧关键词检查也漏掉该缺陷|修复后的独立新会话及逐字引用评分为 pass；历史失败保留，不能用新结果声称旧版本正确|

三项当前复核的引用均回查到原始文件的 SHA256 与 JSON Pointer，见[完整复核依据](analysis/review-results.json)。模型评分只是辅助；本报告的判断同时依赖业务接口、正式状态及实际回答。

### 旧 L1 声明覆盖 L3 的缺陷链路

1. **发现**：人工编辑后的正式记录为“老师”v2；PREF-13 却说“今后称呼您为大哥”，并把老师当作冲突摘要。原检查只判断“老师”和“结论”是否出现，因此误报通过。
2. **定位**：合同模式的原子查询返回原始偏好声明，类型仍为 `preference`，没有明确说明它只是历史证据。Agent 将查询结果误当成当前约定，压过已注入的人工修订正文；旧标题仍含“大哥”又增加了歧义。
3. **修复**：组件提交 `7ef525f` 在保留原话的同时标记历史来源，并提供当前正式条目的正文、版本、条件；应用指令明确正式正文优先于旧原话和标题。删除的正式偏好不会继续以有效偏好进入该查询结果。
4. **验证**：PROTECT-08/09 保存人工版本；PROTECT-10 新建会话；11/12 实际查询并正确区分旧声明和现行正文；13 删除称呼；14–16 新会话只使用剩余报告约定。后续真实 L3 输入再次包含原删除／忽略来源，输出中的旧内容仍未恢复为正式记忆或待确认提示。原始证明分别在 [E10](analysis/records/E10.json)–[E14](analysis/records/E14.json)。

这也修正了此前 README 对 `preferences-02`“修改后真实采用老师”的过强描述。此前那组只完成了流程及薄弱关键词断言，实际回答并不正确；额外追问后能够自我更正，也不能抹掉前一轮失败。

### 其他已记录问题

- 上游自动云 Skill 与本地合同 Skill 重复，曾使 Agent 请求未授权桥接；专用部署仅保留记忆注入，本地合同 Skills 继续使用。
- 三风险并发相关性判断曾遭遇结构化桥接429；已采用同请求、原时限内有界重试，后续实际三风险查询成功。不能据此宣称任何负载都稳定。
- 称呼候选与正式条目的主题在不同时间规范化，曾漏检冲突；统一比较前的主题后，真实变更候选带原条目及版本，用户忽略不影响正式正文。[E21](analysis/records/E21.json)
- 旧审计器只看当前案例版本，曾把仍存在的 `case_history @1` 判为来源缺失；审计副本补充历史证据，原失败文件未覆盖。
- judge 的序列化 JSON 引用容易出现转义／重排不一致；新的复核使用单个原始值和 JSON Pointer。旧的最短四字符校验还会误拒完整 `409`、版本 `2`、空列表 `[]`；现在允许完整短值，但仍拒绝较长值中随意截取的短片段。这是证据校验修复，没有降低人工保护等业务断言。

## 5. 最终结论与适用试用范围

**已有证据支持的能力**：真实风险反馈形成可追溯 L1；同角色相似合同中带条件召回；不同合同处置形成待确认 L2；确认后的经验被真实读取并按当前原文判断；明确长期与临时偏好区分；修复后新会话采用最新人工约定；删除、忽略和同来源再提炼下的服务端保护；当前团队模型的个人隔离及审核共享；反馈同步失败、提炼失败和重启后的恢复。

**原版本确认失败、现已定向修复的能力**：人工修改后，旧 L1 声明曾覆盖最新 L3 的采用。当前定向证据支持修复，但这不证明所有旧记忆冲突、所有自然语言表达、所有长会话都不会再出错。

**仍不足或未覆盖的范围**：

- 测试主要是少量设备采购合同和明确偏好，尚无代表性业务样本、盲测、统计性准确率、召回率或长期漂移结果。
- 复杂审批层级、真实付款／修订执行证据、完整政策文书替代链、广泛风险主题及跨领域原则提炼，不能由此次少数例子外推。
- 修订稿试验没有改变付款／验收条件，也没有替换主合同；相关自动失效链路不能认定已验证。
- 同团队多个合同Agent不是当前产品范围；跨企业验证使用独立应用实例。E2B、远程部署、多节点和持续高并发未在本轮验证。
- 当前仍有“旧标题与最新正文不一致”的展示情况；修复使 Agent 优先采用正文，但未自动改写用户标题。
- 上下文压缩及隔离运行中的配置／会话问题已按用户要求搁置，另行跟踪；本报告不将它们算作记忆质量失败，也不宣称长会话运行验收完成。
- 模型实际解析身份不可独立核验，抽取与judge同模型；没有法律专家盲审证据。本报告验证信息处理链路，不认证法律结论正确性。

因此，**适合进入有限辅助试用**：本机环境、每团队一个合同助手、个人合同默认私有，以相近设备采购业务为起点；用户在真实风险卡片中保存处理意见，经验／偏好继续人工确认，团队内容继续审核，历史建议必须核对当前原文。试用应将“原文事实、历史处理、当前建议、真实审批／执行”分别展示和核查。

**不适合据此直接进入**自动审批、自动修改执行、无需原文核对的企业规则推荐，或以记忆作为权威制度库替代品。当前结论是“已执行实验及定向复核支持上述有限能力”，不是“合同记忆系统整体全部验收通过”。
