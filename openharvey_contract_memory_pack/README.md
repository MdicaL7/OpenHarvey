# 华子合同审批记忆评测包 v1

这是一套原创虚构的中国大陆 B2B 合同与审批记录，用于检验 OpenHarvey 能否从已核实的人类审批中提取经验，并在新合同中按主体、交易角色、适用范围、时间与证据正确引用。它不是签署合同合集，也不是法律意见或可直接用于交易的范本。

包含 10 份可编辑 DOCX 与等价 TXT：6 份历史合同、4 份未来待审合同，共 140 个条款锚点；4 个虚构交易对手。另有 21 条独立审批/政策事件、24 道查询、15 个当前状态记忆金标及逐时点版本。所有公司名均为测试标签，ORG 编号不是工商登记编号。没有真实姓名、身份证、账号、签章或真实付款凭据。

## 先用这一条路径

1. 选择一个干净的测试组织/实例、团队和 Agent。不要在生产团队运行。组织级 L3 也必须隔离；仅新建同组织团队或工作区不能确保清空旧经验。
2. 在本包根目录运行：

   python3 07_tools/materialize_stage.py --stage T5_current_policy --out /tmp/huazi-t5

   此命令只复制本地 TXT，不联网，不调用模型，不上传数据，也不修改应用。输出目录必须为空。
3. 按生成目录中 upload_order_OPERATOR_ONLY.jsonl 的时间顺序上传并实际阅读 UPLOAD_HISTORY_ONLY 中的历史合同、身份映射和逐条审批/政策记录。每个历史合同在其审批记录之前；新政策和撤回在实际发生时再读。采用界面已有附件读取能力，不使用个人偏好 /api/memories 存合同事实。
4. 对历史材料先抽取合同事实，再读审阅意见及最终审批，区分业务提议、机器建议、人工附条件批准和执行证明。不要从合同中“猜”已批准。H03 的保函核验只证明保函条件，不证明合同生效、发票或实际付款。
5. 在体验/候选界面检查记忆候选及证据，人工确认适用范围。记忆发布确认与合同业务审批不是同一件事。已有经验收到新政策或撤回后，通过更新候选、确认或版本化编辑处理旧经验；不要假定 L2/L3 自动失效。
6. 在同一隔离团队的新工作区逐份上传 F01–F04，只提供对应新合同和确有需要的当前政策，不再附上历史合同/审批材料。先完成独立测试，再在另外的综合会话运行 Q24，此题允许同时提供四份未来合同。
7. 使用 04_queries/queries.txt 提问，保留回复、检索轨迹、候选状态与原生证据引用。评测者最后才查看 05_private_gold_DO_NOT_INGEST；该目录绝不能进入 Agent 提示、附件、向量库或自动索引。

人工版可不用脚本：按 00_start_here/temporal_stages_OPERATOR_ONLY.json 中的允许输入逐一选择。建议用脚本，避免把未来更新误读进早期时点。

## 文件边界

- 01_history/contracts_docx 与 contracts_txt：六份历史合同，同一合同选 DOCX 或 TXT 一种，避免重复摄入
- 01_history/identity_map.txt：测试租户的可信主体与别名映射，应作为来源读入
- 02_review_writeback/event_files：21 个可上传的独立事件 TXT；严格按时间读取
- 02_review_writeback/operator_only_indexes：汇总 JSONL/TXT 和重放索引，仅操作员用，不能整包上传做早期时点评测
- 03_future：四份待审合同，每个独立测试只读相应合同；不存在其实际最终批准、签署或付款结果
- 04_queries：只含题目；查询清单本身不要一次性喂给被测 Agent
- 05_private_gold_DO_NOT_INGEST：评测者独占，含抽取答案、记忆/版本、查询要点和预期“建议”，无未来实际审批结果
- 06_negative_controls_QUARANTINE：只在完全独立的另一个租户/组织/服务实例内放置跨租户负例，绝不上传进华子测试团队
- 07_tools：无模型的阶段生成器、静态验证器和结果诊断器
- 08_validation：本地夹具与文档质量检查记录；不代表应用端测试结果

## 时间测试不能回拨已有记忆

五个场景分别重建隔离环境：

- T1_before_guarantee：2026-02-09，Q05，仅有H03附条件批准，无保函核验事件
- T2_after_guarantee：2026-02-13，Q06，保函已核验，但合同生效/发票未证实
- T3_before_withdrawal：2026-04-01，Q08，H04有限许可当时已批准
- T4_internal_withdrawal_only：2026-05-15 15:00，Q09，内部先例已撤回，尚无双方补充约定
- T5_current_policy：2026-08-20，其余问题；已知补充约定、删除证明和七月新采购政策

例：python3 07_tools/materialize_stage.py --stage T1_before_guarantee --out /tmp/huazi-t1

不要在已读七月政策或已发布组织级经验的环境里，仅把问题日期改成二月。每个阶段的金标位于同名 memory_snapshot.jsonl；expected_memories.jsonl 明确是 2026-08-20 当前快照，不能用于早期状态比较。known_from/known_until 表示当时可知的记忆版本；valid_from/valid_until 表示事实或规则适用窗口，二者不可混同。H03 服务结束不抹去其历史批准或存续责任，也不假定原生自动过期。

## 必须另做的运行生命周期检查

上面的独立时点问答检查语义与时间，不能单独证明发布/更新机制真的执行。另用一个全新隔离组织/实例完成连续观察，保存界面或接口返回，不要只问系统“理论上应该怎样”。

1. 读入H03及截至2月8日的审阅/审批，先不确认经验候选。记录候选状态并实际检索，运行Q21。允许L0/L1可见，必须没有把候选当已确认L2/L3。明确候选状态与合同附条件批准可以不同
2. 按顺序推进至4月1日，在撤回和新政策进入之前，显式确认发布H04有限许可及P01基线相关经验。记录这些原生经验ID、层级、版本、条件和证据；这是后续更新测试的旧记录基线
3. 继续按时间读入5月撤回、另行补充及执行记录、6月数据政策、7月采购政策。先观察旧L2/L3是否仍保持原版本；不要假定它已自动变化。在人工更新完成前，用Q22及当前政策问题检查回答是否识别冲突、拒绝继续依旧授权放行；保留检索轨迹
4. 通过应用支持的更新候选、显式确认或版本化编辑处理旧经验。若编辑同一记录，核对ID与版本递增；若发布替代记录，记录新旧ID关联，并明确处理旧记录的状态或适用范围。再次检查新证据、条件及旧审计链，不要求系统具有未实现的自动失效功能
5. 同团队新建未来合同工作区，不附历史资料，再测F03/F04。分别报告“回答有正确更新意识”和“已发布经验状态确实更新”，两者不能混成一个通过

此流程可能触发真实模型作业或经验发布，应在操作员授权下手动执行。本包没有执行上述应用操作。不要同时把已包含更新的当前快照作为模型输入。

## 合同设计与重点

- H01/F01：华子甲方买入启衡终端，可对照对手、标准商品和迟交让步
- H02：华子乙方卖给同一启衡，0.03%变成客户付款迟延；不能只比数字或甲乙标签
- H03/F03：云砺试点与新年度采购，60%预付、专用保函、30%赔偿个案与新政策冲突
- F02：华子成为云砺的乙方供应商，同样30%上限保护的是华子；采购政策不能机械强套
- H04/F04：匿名统计结果的窄许可、先例撤回、另行终止合同许可，以及后来更宽的训练提案
- H05：同一景澍成为委托方，华子成为受托方，不得把对方获许可的历史当作自己的权限
- H06：真实感会务条款作为同团队无关负例，不能支持软件预付款或责任上限

## 已核对的 OpenHarvey 分支适配范围

代码层面参考：codex/contract-memory，commit 0320e814f32cb8f4801a2f4f04422c5012664ea6；配套 MemoryCore commit 41b3e0a68235b2f199acdd1c8f680b858920de5a。本包未在其运行服务执行端到端上传、提取、召回或确认，也未调用外部付费模型。兼容性是源码核对，不是运行通过承诺。

已核实的概念映射：

- L1 原子记录 kind 可为 contract_fact、human_opinion、decision、agent_suggestion、execution_result、preference、open_issue；包括 content、topic、perspective、conditions[]、exceptions[]、source_ids[]、document_refs[]，business_state 为 proposed/confirmed，validity 为 active/withdrawn/superseded
- L2/L3 为 experience/preference；title、content、topic、conditions、exceptions、source_ids 等；id、scope、status、version 由应用管理
- 本包实体、交易对手、时点、授权范围、失效与继承关系是评测语义字段，不是承诺存在的原生结构化筛选器。将必要条件保留在正文/conditions，不能只存“公司名+结论”
- 未确认候选不得当作已确认 L2/L3 通用先例；但 atomic/* 的 L1 和 conversation/* 的 L0 仍可能召回。正确目标是“不误当作批准”，不是“所有层都绝对不可见”
- 同组织的另一个团队未必属于安全隔离租户，L3 可为组织共享。跨租户负例要在隔离组织或服务边界测试
- 新政策/撤回进入L1后，旧L2/L3不一定自动变更；应观察更新候选与人工确认/编辑链，记录版本和证据。没有自动变更不应伪报为自动完成
- /api/contract-memory/review 是团队记忆发布审核，不是合同审批。风险反馈中的接受风险也不能推定自动形成记忆链接
- 上传附件不等于 Agent 已读取。实际读取及原生来源证据形成后，才评估 source-verified；message_only 不能伪装成已验证文档来源

优先使用现有 UI：团队 /experience，合同 /spaces，线程附件与 Labs 中 Contract materials 设置。若手工调试接口，源码里 raw file upload 为 POST /api/workspaces，X-Filename 需 URL 编码，并带 X-Team-Id；候选 GET /api/contract-memory/candidates?team_id&thread_id，确认 POST /api/contract-memory/confirm 要 team_id、id、operation_id；编辑还需版本。这里不是可复制执行的批量导入器，必须以当前服务实际接口与授权为准。确认/创建经验可能排队模型作业并产生费用，本包工具不会调用它们。

## 证据映射与结果保存

H01-C06 等是人为条款锚点，APPROVAL-H01-D1 等是审批来源锚点，M01 等是逻辑金标标识。它们不是 OpenHarvey 的原生证据ID。每次上传/解析后，操作员应记录：夹具文件SHA256 → 原生文档ID → 实际读取块ID（例如运行时生成的 D…B…）→ 对应夹具锚点。不要伪造原生ID，不要把M01写进应用当真实记忆ID。

07_tools/runtime_evidence_mapping.example.jsonl 是空白格式示例。金标 expected_evidence 用于核查来源内容；运行结果可用原生引用经映射归一化评分。允许来源的等价直接证据和多条相关证据。required_memory_ids 是诊断召回目标，不是必须逐字输出的名单；如当前政策已清楚说明替代关系，不强制为正确答案额外召回每条过时经验。

## 评分和防泄漏

详见 00_start_here/SCORING.md。至少分别报告：合同事实抽取、语义相关召回、最终适用判断、时间/更新、证据与拒答，不用“有没有提到华子”作为成功标准。跨租户泄露、编造已批准/已付款、将未批准提议当通用先例、撤回后继续授权，是独立关键失败。

python3 07_tools/validate_pack.py

python3 07_tools/score_results.py --extractions path/to/extractions.jsonl --answers path/to/normalized_answers.jsonl

第二条只做确定性诊断，不读取或调用应用；没有实际预测文件就不能生成应用成绩。评分示例没有真实模型结果。原始回复、原生检索轨迹和人工评分应另存到测试运行目录，不与输入或金标混放。

## 来源与限制

公开来源检索未找到同时具备大陆完整合同、审批历史、跨合同个体记忆和撤回/更新金标的精确匹配集，因此本包原创合成。官方模型只用于结构参考，没有把官方示范合同称为真实已签合同，也未复制公开真实合同中残留的个人信息。来源与候选数据集说明见 00_start_here/SOURCES.md。

样本小、场景是刻意设计的，不代表行业分布、法律有效性或实际审阅准确率。金额与日期自洽不等于适用于真实交易；涉及法域、税务、资质及主体登记仍需专业核验。本包适合第一轮可追溯功能回归，不适合作为唯一验收或法律决策依据。
