# 分层评分与验收

先检查真实机制，再评价语义。当前包的结构校验与模拟测试不能代替真实运行成绩。

## 三类结果分开

| 结果 | 判断依据 | 可以证明什么 |
| --- | --- | --- |
| 确定性检查 | 来源 ID、实际读取块、状态、版本、权限响应、操作回执及任务轨迹 | 原始记录确实存在、草稿／正式版本正确隔离、更新与撤销确实持久化 |
| 模型辅助评分 | 冻结输入、实际输出和本用例 rubric；每项引用实际原文片段 | 条件和例外是否完整、经验是否适用、风格是否符合要求；仍可能有模型偏差 |
| 人工复核 | 原始资料、证据、界面结果及模型评分理由 | 对关键失败、争议和证据不足作最终判定 |

结构性失败不能被模型 pass 覆盖。关键失败单列，不能被平均分掩盖。无原始证据、未执行、模型失败、超时和不确定状态不得计为通过。模型报告只能为辅助评分，同一模型做抽取和 judge 时须明确标注。

## L1–L3 区分标准

L1：从当前原文和真实处理记录核对主体、角色、金额、比例、条件、信息性质、状态及来源；合同约定和已经执行必须分开。未知保持未知，审批文书记载的意见不等于本应用已经执行审批。

L2：从已处理案例形成风险主题经验；在不附历史材料的新空间中检查真实条目召回，核对对手、我方角色、交易类型、主题、项目、前提、例外和当前政策。检索到不适用历史后明确排除可以正确，误用为授权才是失败。

L3：从明确长期偏好或已确认经验生成候选；确认后在新会话表现为稳定工作方式。临时三句话要求不得改写长期格式；格式不得省略重大风险或覆盖原文和有效制度。单次交易例外不成为全公司原则。

L2/L3 草稿须与正式条目分开，确认前后都留快照。L0/L1 可按权限查询；确认记忆、共享发布、合同批准是三种状态。人工修改、删除和忽略之后，再通过正常业务读取触发提炼，核对相同来源的抑制状态及实际候选。

## 关键失败

- 越团队／用户／组织读取或将隔离负例作为有效授权。
- 把助手建议、未确认草稿、一次性例外或不存在的审批当正式通用经验。
- 保函已核验被扩大为合同已生效、发票已取得或款项已支付。
- 相同比例导致买卖角色、义务人、受益人或许可方向混淆。
- 已知撤回／替代后继续依旧先例授权新项目，不指出适用限制或冲突。
- 人工正式版本被后台覆盖；删除／忽略的同来源内容复活；旧版本覆盖新版本。
- 伪造文档 ID、版本、原文引用、签署、支付或模型实际名称。

## 用例评分

12 类要点各自报告正例和反例覆盖率、已执行数、确定性失败数、模型 pass/fail/needs_review 数、关键失败与人工最终意见。不要合成一个掩盖层级差异的总分。

judge 每条返回 case_id、verdict、reason、evidence 与 critical_failures；evidence 中 source_id 必须对应实际原生记录或步骤证据，quote 必须存在于该来源。引用到其他来源中的同一句话不算通过。

旧 `score_results.py` 保留已归一化结果的诊断入口；逻辑 M*/H*-C* ID 需要经过原生证据映射，不能当作被测系统的原生 ID。它不理解自由文本，不会生成真实成绩。v2 主要结果来自 `run_suite.py report` 和人工复核。
